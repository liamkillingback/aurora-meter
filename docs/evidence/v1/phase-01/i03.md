# I03: failed tentative quota work is never billed

Build unit 01c. Core at `26e18b6` plus the uncommitted wave 1a and 1b tree.
Elixir 1.20.1, OTP 29, PostgreSQL 16.13 on port 5490, schema version 6.

Two things had never been shown. First, that work which did real, durable
metering *before* it failed is still not billed: no test made a `with_quota`
callback flush anything. Second, what an untrappable kill actually leaves
behind: no test in either suite killed a process (`open-findings.md` T1), so
every sentence in `docs/` about a killed caller was the author's assertion.

## 1. The callback flushed, then failed

`AuroraMeter.EntitlementsTest`, one test per failure kind. The script inside the
callback is identical in all three; only the last line differs.

```
subscribe tenant to :pro           (ai_generations: hard limit 1000)
with_quota(tenant, :ai_generations, 3, fn ->
  track(tenant, :ops, 4)           real metering work on a second feature
  Flusher.flush()                  it reaches the database while the reservation is open
  assert Storage.load_counter(tenant, :ops, period)            == 4
  assert Storage.load_counter(tenant, :ai_generations, period) == nil   <- Z1
  raise / throw / exit
end)
```

The `nil` on the gated feature is the core half of "pending quota work is
excluded from reporting": a Pro `UsageReporter` reads persisted counters, and
the reservation is not in them even though a flush has just run. Core cannot
run the reporter, so it proves the value the reporter would read; 01d proves the
Pro half against this.

After the failure, in all three cases:

| Observation | Value |
|---|---|
| `AuroraMeter.usage(tenant, :ai_generations)` | `0` (back to its pre-call value) |
| `Storage.load_counter(tenant, :ai_generations, period)` | `nil` |
| a further `Flusher.flush/0`, then the same read | `nil` |
| `Storage.load_counter(tenant, :ops, period)` | `4` (the work it really did is kept) |

The exit case exits with `:timeout` and the throw throws `:nope`; both are
asserted by value, so a different failure cannot pass for the one under test.

## 2. A reservation is never in a flush batch (Z1)

`I03 a reservation is never in a flush batch`, measured on the ETS row itself.
The row shape is `{key, value, pending_flush, pending_gossip, remote, reserved}`.

```
reset the buffer, then Counter.reserve(tenant, :ai_generations, 3, period, nil, true)

:ets.lookup(counters_table, {tenant, :ai_generations, period})
  -> [{key, 3, 0, 0, 0, 3}]        value 3, reserved 3, pending_flush 0
Store.snapshot_flush_batch()  -> nil        the key is not even dirty
Flusher.flush()               -> {:ok, 0}
Storage.load_counter          -> nil
AuroraMeter.usage             -> 3          the local view does include it
```

`value` moves and `reserved` moves; `pending_flush` and `pending_gossip` do not.
That is the whole mechanism: the quota is strict on this node (I04) while
nothing is billed (I03).

## 3. A caller killed with `:kill`

`AuroraMeter.KillTest`, on real connections.
`AuroraMeter.Test.Kill.run/2` arms `:exit_kill_self` at `:before_commit` inside
the callback and asserts the monitor reported exactly `:killed`; a catchable
exit raises instead of passing.

Measured, for a reservation of **3** against the `:free` plan's hard limit of
**50**:

| Moment | ETS row `{value, pending_flush, pending_gossip, remote, reserved}` | `remaining/2` | `usage/2` | database |
|---|---|---|---|---|
| before the call | key cold | 50 | 0 | `nil` |
| after the kill | `{3, 0, 0, 0, 3}` | 47 | 3 | `nil` |
| after the next flush (`{:ok, 0}`) | `{3, 0, 0, 0, 3}` | 47 | 3 | `nil` |

**The leaked quantity is exactly the quantity reserved: 3.** `pending_flush` is
zero, so the flush has nothing to take and the database is untouched, now and
for ever. The cost is local quota: `remaining/2` falls from 50 to 47 and stays
there until the Store restarts or the period rolls over. That is the trade D09
accepts, and it is now a measurement rather than a description.

A second test, `I04 a killed caller's reservation continues to occupy the limit
on that node`, takes the same measurement at the boundary: a killed caller that
had reserved 48 leaves `{48, 0, 0, 0, 48}`, the next two units are still
admitted, the one after that is refused with `{:error, :limit_exceeded}`,
`remaining/2` is 0, and the flush writes **2** (the two real units), never 50.

## 4. C6: `commit_work/5` after a Store restart

`I03 Counter.commit_work after a Store restart raises (C6, fixed in 03b)`. This
test asserts what the code does today, names the defect and names the unit that
fixes it. `v1-release.md` 1.1 requires the suite to stay green and 1.2
requirement 6 forbids hiding a skipped test, so a failing test is not an option.

```
Counter.reserve(tenant, :ai_generations, 2, period, nil, true)   -> :ok
  ets row: {2, 0, 0, 0, 2}
kill AuroraMeter.Store, await the restart
Counter.commit_work(tenant, :ai_generations, 2, period, today)   -> raises
Counter.release_work(tenant, :ai_generations, 2, period)         -> raises
Counter.reserve(tenant, :ai_generations, 2, period, nil, true)   -> :ok   <- the asymmetry
```

**The exact exception, recorded so 03b can assert its replacement.** Both
`commit_work/5` and `release_work/4` raise `ArgumentError` with this message,
character for character:

```
errors were found at the given arguments:

  * 2nd argument: not a key that exists in the table
```

It comes from `:ets.update_counter/3` (`counter.ex:93` and `:107`). It names
neither the tenant nor the feature, which the test asserts directly:

```elixir
refute message =~ tenant
refute message =~ "ai_generations"
```

An operator reading this in production learns that something failed and nothing
about whose work was lost. Inside `with_quota/4` it is raised *after* the
callback has already succeeded, so the caller's work is done and unbillable.

The contrast is the defect: a deferred `Counter.reserve/6` on the same cold key
returns `:ok`, because `reserve_pending/2` calls `ensure_seeded/1` first
(`counter.ex:113`) and `commit_work/5` and `release_work/4` do not. 03b seeds
the row first and flips both `assert_raise` calls.

## 5. The period and day the reservation was counted against

`I03 a reservation committed against a captured day lands in that day's bucket
(partial until 02c)`. Core has no clock seam (`open-findings.md` C11) and this
unit modifies no `lib/` file, so the crossing is expressed by passing the period
and the day explicitly, which is exactly what `with_quota/4` captures at
`entitlements.ex:279-280` before the callback runs.

```
Entitlements.reserve(tenant, :ai_generations, 2, ~U[2026-01-01 00:00:00Z])
  Counter.value(chosen_period)          == 2
  Counter.value(current period)         == 0     the chosen period, not the clock's
  Counter.day_value(today)              == 2     a plain reserve has no captured day

Counter.reserve(..., chosen_period, nil, true)   deferred, 3
Counter.commit_work(..., chosen_period, ~D[2026-01-15])
  Counter.day_value(~D[2026-01-15])     == 3     the captured day
  Counter.day_value(today)              == 2     unchanged
  Counter.value(chosen_period)          == 5
```

**What is outstanding.** This proves the period and day are honoured when they
are supplied. It does not drive a `with_quota/4` callback across a real
midnight, because nothing in `lib/` can be told what time it is. 02c introduces
`AuroraMeter.Clock` and owns the full crossing test; `docs/correctness.md`
records the gap under I03's known limits.
