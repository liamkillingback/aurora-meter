# I01: one flush batch has at most one durable effect

Build unit 01c. Core at `26e18b6` plus the uncommitted wave 1a and 1b tree
(`git diff | sha256sum` recorded in `core-regressions.md`). Elixir 1.20.1,
OTP 29, PostgreSQL 16.13 on port 5490, schema version 6.

Seven tests. Two were renamed from existing ones and keep every numeric
assertion they had; two are new and kill a process.

| Test | Module | Mechanism |
|---|---|---|
| `I01 twelve independent connections deliver one batch once` | `FlushBatchConcurrencyTest` | 12 real connections, one batch id |
| `I01 new deltas arriving during a retry are not lost and are not applied twice` | `FlushBatchConcurrencyTest` | `:after_commit_before_ack` on `FaultStorage` |
| `I01 a commit whose response was lost, then a foreign writer, cannot apply a delta twice` | `FlusherTest` | `:after_commit_before_ack`, foreign write in the predicate |
| `I01 a batch belongs to Store until acknowledged, while later usage stays pending` | `FlusherTest` | retained-batch contract |
| `I01 a graceful shutdown persists pending counters` | `FlusherTest` | `Supervisor.terminate_child/2` |
| `I01 a Flusher killed between the snapshot and the persist keeps the batch in Store` | `KillTest` | `Process.exit(pid, :kill)` |
| `I01 a Store killed before the flush loses the buffered deltas, as documented` | `KillTest` | `Process.exit(pid, :kill)` |

## 1. Twelve deliveries, one effect

Unchanged from the phase-17 case except for its name. Twelve
`Task.Supervisor.async_nolink` workers each take their own non-sandbox
connection and call `AuroraMeter.Storage.flush_batch(id, counters, history)`
with the **same** batch id and a delta of **5**.

Observed: every one of the twelve returns
`{:ok, %{counters: [%{value: 5}], history: [%{value: 5}]}}`;
`Storage.load_counter/3` is `5`; `Storage.load_history/3` is `5`; one row in
`aurora_meter_flush_receipts` for that id. The `5` is a historical assertion and
is preserved verbatim.

## 2. The lost response, then a foreign writer

The phase-17 script, ported by 01b onto `AuroraMeter.Test.FaultStorage` and
renamed here. Its numbers are unchanged and must stay unchanged:

```
track 5                 -> pending_flush 5
flush                   -> the batch commits 5
                           the :when predicate writes a foreign +3 straight to the
                           database, then :after_commit_before_ack raises
                        -> the caller sees {:error, _}; the batch stays pending
track 2
flush                   -> the receipt refuses the redelivery, totals are read back
   Storage.load_counter == 8      (5 committed + the foreign 3)
   Counter.value        == 10     (8 plus the 2 still pending)
flush
   Storage.load_counter == 10
```

The test also captures the batch id with `Store.snapshot_flush_batch/0` before
the flush and asserts **exactly one** `aurora_meter_flush_receipts` row for it at
the end: one durable effect, however many times the batch was sent.

`Faults.assert_fired!(:after_commit_before_ack, owner: flusher)` is asserted, so
an armed-but-unreached fault cannot make this pass. Example batch id from
`logs/01c-seed-1.txt`: `04d0ab72-fade-4f8f-a776-008004090640`, tenant
`org_2309`.

## 3. Interleaved new deltas during the retry

This is `v1-release.md` section 17's third I01 requirement, which had no test.
The interleaving, in the order the test performs it:

```
t0  track 5
t1  Store.snapshot_flush_batch()            batch A, counters [5], history [5]
t2  flush, :after_commit_before_ack raises  A committed; caller sees {:error, _}
                                            A is still in Store's pending slot
t3  track 3                                 pending_flush 3 on a key whose batch
                                            has already been taken
t4  Store.snapshot_flush_batch().id == A    the retained batch, not a new one
t5  flush                                   A re-sent under the same id;
                                            the receipt dedupes it
        Storage.load_counter == 5           not 10
        Counter.value        == 8           rebased on 5 plus the 3 pending
t6  Store.snapshot_flush_batch()            batch B, id != A
t7  flush
        Storage.load_counter == 8
        receipts for A == 1, receipts for B == 1
```

Example batch id for A from `logs/01c-seed-1.txt`:
`72447414-ae80-4b36-bb99-041371815558`, tenant `flush_batch_2115`.

The three are neither lost (they reach the database at t7) nor applied twice
(the database reads 5 at t5, not 8).

## 4. Killing the Flusher (Z4)

```
track 6
Store.snapshot_flush_batch()      -> batch A, published into :aurora_meter_flush_batches
Process.exit(flusher, :kill)
{:DOWN, _, :process, pid, :killed} -- asserted to be exactly :killed
Kill.await_restart!(Flusher, from: pid)  -> a different pid
:ets.lookup(Store.flush_batches_table(), :pending) -> [{:pending, A}]
flush                              -> Storage.load_counter == 6
                                      receipts for A == 1
```

The Flusher owns no table, so killing it loses nothing. The restarted Flusher
re-sends the identical batch id rather than rebuilding one from whatever is
pending at that moment.

## 5. Killing the Store (Z5)

```
track 6
Store.snapshot_flush_batch()      -> batch A retained
track 2                            -> buffered behind A
Process.exit(store, :kill)
{:DOWN, _, :process, pid, :killed} -- asserted to be exactly :killed
Kill.await_restart!(Store, from: pid)
:ets.lookup(Store.flush_batches_table(), :pending)     -> []
Store.snapshot_flush_batch()                           -> nil
:ets.lookup(Store.counters_table(), {tenant, :ops, p}) -> []
Storage.load_counter                                   -> nil
receipts for A                                         -> 0
flush                                                  -> {:ok, 0}
Storage.load_counter                                   -> nil
```

Both the retained batch and the two buffered units are gone, because the Store
owns the tables and `one_for_one` hands the restarted process new, empty ones.
Nothing was written, so nothing was written twice either. This is the documented
buffered-loss boundary (`architecture-map.md` section 12, I01's known limits in
`docs/correctness.md`), not a defect, and the test's own description says so.

## 6. Both `:DOWN` reasons

Both kill tests assert `{:DOWN, ^reference, :process, ^pid, :killed}` with the
reason matched literally, so a catchable exit can never be mistaken for
untrappable death (G01 bullet 2). `AuroraMeter.Test.Kill.run/2` makes the same
assertion for the worker kills in I03 and I04.
