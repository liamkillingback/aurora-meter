## 4. Results

### 4.1 The model's rules, against the line each mirrors

The model is a reimplementation, not a delegation: it calls neither
`AuroraMeter.Credits.Ledger` nor `AuroraMeter.Credits.Promotions`. A reviewer can
check it against the source with this table and without reading both in full.

| Model rule (`ledger_model.ex`) | Mirrors |
|---|---|
| `write/2`: `balance_after = balance + amount` | `ledger.ex:436` |
| `write/2`: `held_after = held + held_delta` | `ledger.ex:437` |
| `write/2`: `promotional \|> promotional_delta \|> min(max(balance_after, 0)) \|> max(0)` | `ledger.ex:439-444` |
| `promotional_delta/2` clause 1: a promotional grant adds its amount | `ledger.ex:474-475` |
| `promotional_delta/2` clause 2: `:reversal` leaves the figure alone | `ledger.ex:481` |
| `promotional_delta/2` clause 3: any other negative amount subtracts | `ledger.ex:483-484` |
| `promotional_delta/2` clause 4: everything else leaves it | `ledger.ex:486` |
| `sufficient?/2`: `balance - held + tolerance >= amount` | `ledger.ex:489-490` |
| grant: a known reference returns `:duplicate` with no write | `ledger.ex:96-98`, `:112` |
| hold: duplicate checked **before** sufficiency | `ledger.ex:124-131` |
| settle/release: the hold row decides `:not_found` / `:already_settled` before the balance row is touched | `ledger.ex:149-154`, `:506-518` |
| settle: `amount: -actual`, `held_delta: -hold.held_delta`, `overrun = actual > held_delta` | `ledger.ex:157-167` |
| release: `amount: 0`, `held_delta: -hold.held_delta` | `ledger.ex:183-191` |
| debit: duplicate, then sufficiency; `category` nil (L14) | `ledger.ex:205`, `:220-225` |
| reverse: the `:debit` namespace, never refused for balance (L2) | `credits.ex:329-335`, `ledger.ex:221-222` |
| expiry: `min(remaining, promotional, max(balance - held, 0))`, floored at 0 | `ledger.ex:296-298` |
| expiry: `fully_expired? = amount >= remaining` | `ledger.ex:299` |
| expiry: `amount == 0 and not fully_expired?` refuses, writing nothing | `ledger.ex:304-305` |
| expiry: `expired_at` stamped only when fully expired | `ledger.ex:321-323` |
| expiry: `now` truncated to the second (L12) | `ledger.ex:249` |
| attribution: a promotional grant contributes `min(amount, max(balance_after - total, 0))` | `promotions.ex:19` |
| attribution: a reversal's consumption is `total - min(total, max(balance_after, 0))` | `promotions.ex:33` |
| attribution: any other negative entry's is `total - max(total + amount, 0)` | `promotions.ex:34` |
| attribution: an expiry consumes only its own grant | `promotions.ex:38`, `:44-46` |
| attribution: anything else spends soonest-expiring, then oldest, then id | `promotions.ex:48-61` |
| attribution: a non-expiring grant sorts last | `promotions.ex:63` |
| `wallet/1`'s shape | `credits.ex:142-175` |

Thirteen self-tests pin the model without a database (`describe "the model
itself"` and `describe "the dormant lot view"`). They deliberately do **not**
carry an `I10 ` prefix: they prove the oracle, not the ledger, and a name that
claims an invariant it does not prove is exactly what `correctness_index_test.exs`
exists to catch. `docs/correctness.md` names them in I10's Prerequisites instead.

Three things the model deliberately does not model, each stated in its moduledoc:
wall-clock timestamps (it predicts order, never a stamp), the real UUID identity
of a grant (it keys by reference, so `promotions.ex:53`'s "then id" tie-break has
no counterpart), and the generated partial-expiry reference (`ledger.ex:354-357`).

### 4.2 The generator

`command/2` is state-dependent: it holds its own model and draws only from what
is legal, plus a measured share of what is not. Weights, before the state filters:

| Command | Weight | Offered when |
|---|---|---|
| grant | 5 | always |
| hold | 4 | always (an unaffordable amount when the wallet is empty) |
| debit | 3 | always |
| reverse | 2 | always |
| settle | 4 | at least one hold exists |
| release | 2 | at least one hold exists |
| `expire_due` | 3 | at most one grant is due at the chosen instant (L19) |

Within a command: a reference is fresh four times in five and an existing one the
fifth, which is how duplicate-reference and `:already_settled` paths are reached;
a hold or debit amount is affordable four times in five and exactly one
micro-dollar too much the fifth, which is the `sufficient?/2` boundary; a settle
is at or below its hold four times in five and an overrun the fifth; a
settle/release reference is a real hold five times in six and an unknown one the
sixth. Amounts are `1..50_000_000` with a weighted tail at `1`, `9_999`, `10_000`,
`999_999`, `1_000_000`, `1_000_001` so cent boundaries appear. Expiry offsets are
whole seconds (60 s, 1 h, 1 d, 7 d, 30 d) from `~U[2026-01-01 00:00:00Z]`, because
`expires_at` is a second-precision column.

Every draw, references included, comes from StreamData. Nothing calls
`Enum.random/1`: a source of randomness the shrinker cannot see would shrink into
a history that is not the one that failed.

Measured over the 1399 histories of deep run 3b: 3 to 40 commands, median 15.
(Three is below the declared floor of five because StreamData's shrinker produces
shorter histories than the generator does; the generator's own floor is five.)

### 4.3 The invariants checked after every step

| Id | Checked |
|---|---|
| V1 | `balance` equals `sum(amount)` over the tenant's rows |
| V2 | `held` equals `sum(held_delta)` over all rows **and** `sum(held_delta)` over holds still `:pending` |
| V3 | `0 <= promotional <= max(balance, 0)` |
| V4 | the newest row by `(inserted_at, id)` carries the balance row's three figures |
| V5 | no two rows of one `kind` share a non-null reference |
| V6 | every hold is `:pending`, `:settled` or `:released`, a settled hold has its `settled_amount`, and the ledger's status matches the model's |
| V7 | the returned value, `Credits.balance/1`'s full map, and every promotional grant's remainder as `Promotions.remaining/2` computes it |
| V8 | the lot view's own conservation: per lot `available + reserved + consumed + reversed + expired == amount` with no negative bucket; across lots `sum(available + reserved) - debt == balance`, `sum(reserved) == held`, `sum(available + reserved over promotional lots) == promotional`, `sum(expired) == expired`, each against a scalar the replay tracks independently of the buckets |

V7's attribution half is the sharpest of these: the model computes each
promotional grant's remainder from its own rewritten fold, and the executor
computes it by calling the real `AuroraMeter.Credits.Promotions` over the rows in
the ledger's own order, exactly as `Ledger.remaining_on_grant/3`
(`ledger.ex:340-349`) does. The two implementations are compared at every step of
every history.

### 4.5 The measured L1 leak

`LedgerModel.lot_view/1` replays the same history with 06a's lot semantics and
reports two figures per history, both written to `logs/01e-leaks.jsonl`:

- `l1` (`released_expired`): value that was reserved when its lot expired and
  became `expired` in the lot design, while today's ledger hands it back as
  spendable balance on release. **This is L1 and nothing else.**
- `leak`: the raw difference between the two spendable figures, which also carries
  this view's two deliberate divergences (06a's `debt` applied to commands 06a
  would have refused, and a reversal that eats into a reservation).

A third figure, `reserved_at_expiry`, records how much was still reserved on a lot
at the moment it expired. `l1` can only be non-zero when that is, so a run that
measures no leak can say whether its histories never held a reservation across an
expiry or simply never closed the hold afterwards.

Over the 1399 generated histories of deep run 3b:

| | |
|---|---|
| histories that held a reservation across a lot's expiry | 61 (4.4%), 692,619,407 µ$ reserved at those moments |
| histories with a non-zero `l1` | **26 (1.9%)** |
| total L1 leak | **214,506,669 µ$ ($214.51)** |
| largest single-history L1 leak | **32,982,808 µ$ ($32.98)** |
| mean L1 leak across the histories that had one | 8,250,256 µ$ ($8.25) |
| histories with a non-zero raw `leak` | 161 |
| raw `leak` range | -22,862,793 to +42,004,230 µ$ |
| histories that reached a non-zero `debt` in the lot view | 445 |
| total value expired in lot terms | 2,769,141,189 µ$ |

So roughly one generated history in fifty hands spendable balance back to a tenant
out of a grant that has already expired, and the largest single instance in this
run was $32.98 on a wallet whose grants are at most $50. That is the size of L1,
measured rather than argued.

(Deep run 2 measured `l1` at zero across 610 histories. That was a sample-size
artifact of a shorter run, not a different result: the same code measured 26 in
1399. It is recorded because a zero that later turns out to be a sample artifact
is exactly the kind of number that gets quoted.)

The negative raw leaks come from the reversal-into-`reserved` rule and are
explained in finding X-01e-2. The raw `leak` and `l1` are reported separately for
that reason: only `l1` is L1.

### 4.6 Deep runs, and every counterexample

Three deep runs were made. All three are reported, including the one that was
invalidated by a fault in this unit's own harness, because a run that was thrown
away is part of what happened.

**Deep run 1** (09:50:07-09:51:03, seed 20260914, 500 runs, 56 s, exit 2). Five
failures. The first was a genuine disagreement; the other four were a cascade.
The cascade's cause was a defect in **this unit's harness**, not in the ledger:
the four named conservation properties pass `cleanup: false` so they can read the
aggregates after the run, and when `run/2` raised there was no caller left to hand
the rows to, so the tenant was never cleaned. `Credits.expire_due/1` is not tenant
scoped (`ledger.ex:251-259`), so every leaked promotional grant made the next
history's expiry count wrong: the executor's foreign-due guard reported 30, then
60, then 61 leftover grants and the run reported four consequences of one cause.
Fixed by a `rescue` in `run/2` that cleans up and re-raises. The run was discarded
and the database cleared (319 transactions, 102 balance rows deleted).

One artifact of run 1 is unexplained and is recorded rather than dismissed:
`logs/01e-observation-run1-2-*.exs` shows a history whose **first** command, a
grant on a freshly allocated `model_<n>` tenant, returned `{:ok, :duplicate}` with
a balance already reflecting that history's first and third commands. No mechanism
in the ledger or the harness accounts for a fresh tenant holding rows. It was not
reproduced on a clean database in runs 2 or 3, it was recorded during the cascade
above, and it is filed as an open question, not as a defect (finding X-01e-3).

**Deep run 2** (09:52:56-09:54:02, seed 20260914, 500 runs, 66 s, exit 2), on a
cleaned database and with the harness leak fixed. Three failures, **all one
defect**:

| Property | Failed after | Step | Problems |
|---|---|---|---|
| `I10 a generated history including expiry matches the pure model` | 2 runs | 17 of 34 | `V4: balance_after -25518830 != -25518829` |
| `I10 a generated history of grants, holds, settles, releases, debits and reversals matches the pure model` | 67 runs | 11 of 13 | `V4: balance_after 32360809 != -9677044`, `V7 attribution: g1 model 0 vs Promotions 12724167` |
| `I10 the newest row's snapshot columns equal the balance row` | 29 runs | n/a | same signature |

The saved counterexample carries the rows it failed on, and they say what
happened. In tenant `model_35906` the four committed rows, listed in the ledger's
own `(inserted_at, id)` order, are:

| reference | written at step | `inserted_at` | `balance_after` |
|---|---|---|---|
| `g20` | 17 (last) | `2026-09-14 09:53:18.928086Z` | -25,518,829 |
| `v3` | 3 | `2026-09-14 09:53:19.848363Z` | -47,824,853 |
| `g5` | 4 | `2026-09-14 09:53:19.857231Z` | -44,103,801 |
| `g16` | 14 | `2026-09-14 09:53:19.912292Z` | -25,518,830 |

The arithmetic is right in every row and the balance row is right. What is wrong
is the **order**: the row written last carries a stamp about 0.98 seconds earlier
than a row written three commands before it. The host's wall clock stepped
backwards, and `apply_entry/3` stamps `inserted_at` from `DateTime.utc_now()`
(`ledger.ex:452`). This is **finding L20**, and it is a real ledger defect: the
second failure above shows its financial consequence, where the ledger's own
attribution believed a promotional grant still had 12,724,167 µ$ that had already
been spent.

**Verdict on every counterexample found: ledger defect, not model defect. One
defect, L20, three times. Fixing unit: 06a.**

Disposition of the three saved files. A seed file's contract in this unit is a
history that replays deterministically; a backwards clock step is not something a
replay can schedule, and all three files replay green. They are therefore filed as
evidence artifacts (`logs/01e-observation-run*.exs`) rather than kept as
regression inputs, and L20 is instead proved deterministically by
`test I10 a backwards step in the wall clock leaves a promotional grant that can
never expire (L20, fixed in 06a)`, which constructs the row state a clock step
produces (by moving one committed row's `inserted_at`, changing nothing under
`lib/`) and drives the real `Promotions` fold and the real `expire_due/1` over it.
No seed file was deleted to make a suite green.

Because the property cannot schedule a clock step and must not report one as an
arithmetic disagreement, the executor now detects the signature exactly (the rows
carry the same multiset of amounts the model wrote, in a different order, which
only a reordering can produce) and abandons that history as **inconclusive**,
counting it. `AuroraMeter.CreditsModelTest`'s `setup_all` prints the count and the
timestamps at the end of every run, so a run that covered fewer histories than it
asked for says so. Silence is never read as success.

**Deep run 3a** (09:59:39-10:01:59, 143 s, exit 2) found no disagreement between
the model and the ledger, and two faults in **this unit's own test code**:

- Two properties hit ExUnit's default 60-second-per-test timeout. The deep
  configuration runs twenty times the default's histories; earlier deep runs had
  passed `--trace`, which silently sets the timeout to infinity, so the budget had
  never been tested. A timeout kills the test process mid-history, so no cleanup
  runs and committed rows are left behind, and the module's row-count guard then
  failed for that reason rather than the one it exists for. Fixed with
  `@moduletag timeout: 600_000` (a guard against a hang, not a budget) and a
  `setup_all` that clears this unit's own `model_` prefix before taking the
  baseline, so a killed run cannot poison the next one. Recorded as finding
  X-01e-5 because it applies to any unit that runs a long property.
- The shrinker produced a history consisting entirely of refusals
  (`[{:hold, "h1", 1}, {:expire_due, _}, {:expire_due, _}, {:expire_due, _},
  {:hold, "h5", 1}]`): every command was refused, so not one row was written,
  there was no newest row, and the V4 and V5 laws crashed on `nil` instead of
  asserting anything. That is a real shape the generator produces and the laws now
  handle it: with no entries, the law is that the model wrote nothing either.

**Deep run 3b** (10:04-10:07, seed **20260914**, `AURORA_PROPERTY_RUNS=500`,
**191 s**, **exit 0**): `Result: 30 passed (6 properties, 24 tests)`, running both
`credits_model_test.exs` and `credits_regressions_test.exs`.

**Five histories were abandoned as inconclusive** because the wall clock stepped
backwards mid-run, and the run said so on stdout with each one's tenant, step and
row timestamps. The two main properties therefore compared roughly 995 of the 1000
histories they asked for, and the four conservation properties roughly 400 of 400.

**Explicitly, what was not found: no disagreement between the model and the ledger
in 1399 histories at seed 20260914, beyond L20.** Every counterexample this unit
produced, across three deep runs, was L20.

### 4.8 Row-count conservation

Both test modules take `Connections.row_counts()` in `setup_all` and compare it in
`on_exit`, raising if anything was left behind. `cleanup!/1` is bounded to the
history's own `model_<integer>` prefix and refuses a prefix shorter than four
characters. The database held 0 credit rows before this unit's work and 0 after
each completed run.

## 5. Changes

No public API, configuration key, migration, telemetry event or operational
procedure changed. Two test-support modules, two test modules and one data
directory were added; `test/` is excluded from the Hex archive, so none of it
ships (`package/0`'s `files:` list in `mix.exs`).

One build-configuration addition: `test_ignore_filters/0` in `mix.exs`, matching
`regressions/seeds/*.exs`. Elixir 1.20 warns on every `mix test` about any `.exs`
