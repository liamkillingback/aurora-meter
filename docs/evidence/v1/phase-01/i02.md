# I02: counter, day history and receipt update atomically

Build unit 01c. Core at `26e18b6` plus the uncommitted wave 1a and 1b tree.
Elixir 1.20.1, OTP 29, PostgreSQL 16.13 on port 5490, schema version 6.

Before this unit I02 could not be proved at all. The only test that made
`flush_batch/3` fail did it by passing an invalid `Date`, which fails in Ecto's
changeset layer rather than in the database, and only the history statement
could be reached that way. `AuroraMeter.Test.FaultRepo` (01b) fails one named
statement *inside* the real `repo().transaction/1`, so Postgres does the
rollback and the assertion is about what a different connection can see.

## The three statements

`AuroraMeter.Storage.Ecto.flush_batch/3` (`storage/ecto.ex:20-55`) issues, in
order, inside one transaction:

| Order | Call | `FaultRepo` statement name |
|---|---|---|
| 1 | `repo().insert_all(FlushReceipt, ...)` | `:receipt_insert` |
| 2 | `add_counters/1` -> `repo().insert_all(Counter, ...)` | `:counter_upsert` |
| 3 | `add_history/1` -> `repo().insert_all(History, ...)` | `:history_upsert` |

Statements 2 and 3 run only when the receipt insert reported one new row.

## How each test is armed

`AuroraMeter.StatementsTest`, `async: false`, `@moduletag :fault`, not
`DataCase`. The test process takes one non-sandbox connection and lends it to
the Flusher with `Ecto.Adapters.SQL.Sandbox.allow/3`, so the flush is driven
through `AuroraMeter.Flusher.flush/0`, the production entry point. Every fault
therefore names the Flusher pid as its `owner:`, because the storage callback
runs in that process and carries no `$callers` back to the test.

```elixir
Config.with_config([{:aurora_meter, :repo, FaultRepo}], fn ->
  Faults.arm(:before_commit, :raise,
    owner: flusher, count: 1, label: statement,
    when: &(&1[:statement] == statement and &1[:kind] == :write))

  assert {:error, _reason} = Flusher.flush()
  Faults.assert_fired!(:before_commit, owner: flusher)
end)
```

Every assertion afterwards runs inside `Connections.run(1, fn _ -> ... end)`,
that is on a connection checked out **after** the aborted transaction ended.
That is what makes this I02 rather than a smoke test: the asserting connection
never saw the transaction that was rolled back.

## Results

A tracked quantity of **5** for `:ops`, one period counter row and one day
history row per batch.

| Statement failed | counter row | history row | receipt row | after the retry |
|---|---|---|---|---|
| `:receipt_insert` | `nil` | `nil` | 0 | counter 5, history 5, receipts 1 |
| `:counter_upsert` | `nil` | `nil` | 0 | counter 5, history 5, receipts 1 |
| `:history_upsert` | `nil` | `nil` | 0 | counter 5, history 5, receipts 1 |

In every case `Flusher.flush/0` returned `{:error, _}`,
`[:aurora_meter, :flush, :error]` was emitted (the "flush failed; the same batch
will be retried" line is in `logs/01c-faults.txt`), and
`Store.snapshot_flush_batch().id` still equalled the original batch id, so the
delta was retained rather than lost.

## Ordering: no statement after the one that failed

`I02 a failing receipt insert writes nothing and reaches no later statement`
arms the fault with `count: :infinity` and a predicate that records every write
statement it is asked about before deciding. The predicate is documented to run
exactly once per check, in the checking process, and there is a single checker
here, so the record is complete.

Observed reached statements: `[:receipt_insert]`. Neither `:counter_upsert` nor
`:history_upsert` was ever reached, which is the `if inserted == 1` guard at
`storage/ecto.ex:31` doing its job.

## The retry applies the deltas exactly once

`I02 a retry after a failed statement applies the deltas exactly once`:

```
track 5
Store.snapshot_flush_batch()   -> batch A
flush, :counter_upsert raises  -> {:error, _}; nothing written
Store.snapshot_flush_batch().id == A        the same batch, not a new one
flush                          -> {:ok, _}
    Storage.load_counter == 5               five, not ten
    receipts for A       == 1
flush                          -> {:ok, 0}
    Storage.load_counter == 5
```

## Conservation

Every test calls `AuroraMeter.Test.Connections.report!/1` after giving back
every row it owns. `logs/01c-faults.jsonl` holds 12 records (four from
`StatementsTest`, five from `KillTest`, three from the 01b harness self-tests)
and **every delta in every record is zero for every table**.

## Known limits of this proof

Atomicity is proved for the Ecto adapter on PostgreSQL. It is a per-batch
property, not a per-`track/4` property: the ETS increment that produced the
delta is not part of the transaction and is not rolled back by a failed flush,
which is why the retained batch matters and why the tests assert it.
