# I11 (phase-01 contribution): holds cannot spend the same available funds twice

Build unit 01c. Core at `26e18b6` plus the uncommitted wave 1a and 1b tree.
Elixir 1.20.1, OTP 29, PostgreSQL 16.13 on port 5490, schema version 6.

**Path note.** `invariant-map.md` gives I11 one home, core

## The renames

Two existing tests keep every assertion and gain the invariant prefix:

- `I11 twenty concurrent $0.10 holds against $1.00 admit exactly ten`
- `I11 concurrent settle and release of one hold: exactly one wins`

A third moved to I10, whose guarantee it actually measures:
`I10 a refusal does not destroy the caller's own transaction`.

## The new hot-wallet test

`I11 fifty independent connections holding against one hot wallet admit exactly
the funded count`.

### The arithmetic, and why it runs in two waves

`AuroraMeter.Test.Connections.run/3` refuses more tasks than the pool can serve,
with the arithmetic in the error message rather than as a checkout timeout
several layers away:

| Quantity | Value |
|---|---|
| `repo().config()[:pool_size]` (`config/config.exs:28`) | 30 |
| connections `Connections` reserves (test process, sandbox owner, cleanup) | 4 |
| `Connections.max_tasks()` | 26 |
| tasks per wave | 25 |
| waves | 2 |
| hold attempts | 50 |

The wallet is the same in both waves and the admitted count is asserted
cumulatively, so the property under test (two holds cannot spend the same
available funds) is exercised across all fifty attempts. Within a wave, 25
transactions contend on the one `FOR UPDATE` balance row lock
(`ledger.ex:410-429`).

### Funding and result

| Quantity | Micro-dollars |
|---|---|
| grant | 2 500 000 ($2.50) |
| each hold | 100 000 ($0.10) |
| affordable holds | 25 |

Observed over the 50 attempts:

| Observation | Value |
|---|---|
| `{:ok, _}` | 25 |
| `{:error, :insufficient_credits}` | 25 |
| `Credits.balance(tenant).balance` | 2 500 000 |
| `Credits.balance(tenant).held` | 2 500 000 |
| `Credits.balance(tenant).available` | 0 |
| hold entries in `Credits.history/2` | 25 |
| `held_after` sequence (sorted) | 100 000, 200 000, ... 2 500 000 |

The `held_after` sequence is the assertion that matters. Twenty-five distinct
running totals, each 100 000 apart, means every hold saw the one before it: a
repeat, or a gap, is what two holds spending the same funds looks like in the
ledger. The test asserts the full sequence, not just the count.

## What this does not prove

The callback-versus-reconciler race (a hold's terminal transition racing a
sweeper) is 05b's, and its test is listed as
`PLANNED (05b)` in `docs/correctness.md`. This file covers the concurrency half
only, on one node, against one wallet.
