# I04: a local hard quota cannot oversubscribe completed plus pending work

Build unit 01c. Core at `26e18b6` plus the uncommitted wave 1a and 1b tree.
Elixir 1.20.1, OTP 29, PostgreSQL 16.13 on port 5490, schema version 6.

The plan under test is `AuroraMeter.TestPlans`:

| Plan | `:ai_generations` |
|---|---|
| `:free` (the default plan) | `limit 50, :hard` |
| `:pro` | `limit 1_000, :hard` |

## 1. Concurrency at the cap

`I04 sixty concurrent with_quota calls against a limit of fifty admit exactly
fifty on one node` (renamed; the assertions are unchanged).

```
60 calls, max_concurrency 20, limit 50
  {:ok, :done}                 -> 50
  {:error, :limit_exceeded}    -> 10
  AuroraMeter.usage            -> 50
```

`I04 Counter.reserve blocks at the hard limit and rolls the increment back`
(renamed) covers the single-caller path: two reserves against a limit of 2
succeed, the third returns `{:error, :limit_exceeded}` and `Counter.value/3` is
still exactly `2`, so a refused reserve leaves the counter where it was.

## 2. Failures give the capacity back

Three renamed tests, one per catchable kind. Each reserves against `:pro`, the
callback fails, and `AuroraMeter.usage/2` is `0` afterwards:

| Test | Failure |
|---|---|
| `I04 a raising callback releases its capacity` | `raise "boom"` |
| `I04 a throwing callback releases its capacity` | `throw(:nope)` |
| `I04 an exiting callback releases its capacity` | `exit(:timeout)` |

The exit case is the one that matters in production: a `GenServer.call`, a
`Task.await` and a database checkout all time out by exiting rather than
raising, and an exit unwinds straight past a `rescue`.

## 3. The measured cost of a killed caller

`I04 a killed caller's reservation continues to occupy the limit on that node`
(`AuroraMeter.KillTest`). The caller is killed with `Process.exit(pid, :kill)`
through `AuroraMeter.Test.Kill.run/2`, which asserts the `:DOWN` reason is
exactly `:killed`.

Limit 50. The killed caller had reserved **48**.

| Moment | ETS row | `remaining/2` | database |
|---|---|---|---|
| before | cold | 50 | `nil` |
| after the kill | `{48, 0, 0, 0, 48}` | 2 | `nil` |
| `reserve(tenant, :ai_generations, 2)` | `{50, 2, 2, 0, 48}` | 0 | `nil` |
| `reserve(tenant, :ai_generations, 1)` | refused, `{:error, :limit_exceeded}` | 0 | `nil` |
| after `Flusher.flush/0` | | 0 | **2** |

**The measured reduction in `remaining/2` is exactly the quantity the killed
caller reserved.** For the 3-unit case in `i03.md` it is 50 to 47; here it is
50 to 2. The limit still admits exactly the cap on this node, counting completed
plus in-flight work: the invariant holds, and what the kill costs is that 48 of
the 50 are in flight for a caller that no longer exists.

Only **2** is ever written to the database, because the 48 are in `reserved` and
never in `pending_flush`. The leak is a local-quota effect and not a billing
effect, which is the distinction `docs/correctness.md` has to keep and now has a
number for.

The reservation clears when `AuroraMeter.Store` restarts or the period rolls
over. There is no cleanup after untrappable termination and the documentation
does not promise one.

## 4. What is not claimed

Per node, against that node's view. On a cluster the cap can be exceeded by what
the other nodes admitted since the last announcement this node applied; that
overshoot is measured in `i05.md`. Aurora Meter does not claim a strict global
quota. A `:metered` feature is never refused by design and a `:counter` feature
has no denominator, so neither participates in this invariant.
