# I07: conflicting reuse of event identity is rejected

**Owner:** build unit 03b. **Contributor:** 03e (corrections reuse the same
resolution). **Gate:** G03.

## What is guaranteed, as of 03b

An `event_id` is a caller's identity for one fact, unique per tenant across
every feature. Submitting it a second time with the **same** payload is a
duplicate. Submitting it with **any** changed field is
`{:error, {:conflict, existing}}`, and nothing is written: not the conflicting
event, not a totals delta, not an export intent, and in a batch not the other
elements either.

"The same payload" is decided by a sha256 over the canonical tuple
`{feature, quantity, occurred_at, kind, original_event_id,
canonical_json(dimensions), canonical_json(metadata)}`, encoded as a canonical
JSON array with object keys sorted recursively by their encoded bytes. Two maps
that differ only in insertion order are the same payload. A map with an atom
key is refused before it is hashed, rather than stringified into a different
payload that shares an identity.

## Prerequisites

Core schema version 8: the unique index on `(tenant_key, event_id)` is what
makes the refusal a property of the database rather than of application code,
on any connection and in any order. Without it the hash comparison is a race.

## Known limits

- **`AuroraMeter.track/4` has no identity to conflict with.** It generates a
  fresh `track:` id per call, by design; a host that needs deduplication on
  that path must use `record/4`. 03c documents the legacy identity rule.
- **Identity is the caller's to choose.** Nothing detects two different facts
  that a caller deliberately gave the same id, beyond refusing the second.
- **An unknowable outcome is reported, not guessed.** When the insert skips a
  row the transaction cannot then see, the answer is
  `{:error, {:unavailable, :conflict_unresolved}}` and the caller retries with
  the same id. See `03b-conflict-wait.md` for when Postgres can produce that
  state (a concurrent delete of the conflicting row) and when it cannot (the
  ordinary race, where `ON CONFLICT DO NOTHING` waits).

## Measured

Twelve independent, non-sandbox connections submitting one identity with **two
different payloads**, seed 0 (`03b-concurrency.json`):

| Outcome | Count |
|---|---|
| `:inserted` | 1 |
| `:duplicate` | 5 |
| `{:conflict, existing}` | 6 |
| `conflict_unresolved` | 0 |
| **rows afterwards** | **1** |
| totals | one row, quantity equal to the winner's, events 1 |

Every task that returned `{:ok, event, outcome}` came back with the payload that
is actually stored. No task saw a duplicate for a payload that is not there.

Five single-field changes, each asserted to conflict: quantity, `occurred_at`,
feature, a dimension value, a metadata value.

## Tests

Indexed in `docs/correctness.md` under I07. In short:

- `AuroraMeter.RecordTest`: the id rules (missing, oversized, non-UTF-8,
  reserved prefix, 128 bytes of multi-byte characters), the canonical form
  (recursive key sorting, order-independent hashing, the microsecond the column
  stores), the five conflicting changes, and identity across features in one
  tenant. Plus a property: two different payloads never share an encoding, and
  key order never changes one.
- `AuroraMeter.RecordBatchTest`: repeated ids with equal payloads collapse;
  with different payloads they are refused before any database call; one
  conflicting element rolls the whole batch back.
- `AuroraMeter.RecordConcurrencyTest`: the twelve-connection two-payload race
  above.
- `AuroraMeter.MigrationV8Test` (03a): the index itself.

## Negative controls

`03b-controls.json`. C2 replaces the payload-hash comparison with `true`, which
is exactly the "simplification" the build document names as the single largest
residual risk of this unit, and the conflict tests fail. Restored and verified
by hash.
