# I08: one input source yields one commercial usage effect

Owner: build unit **03c**. Contributors: 03b (the projection), 04c (the Pro
cutover). Indexed in `docs/correctness.md` under "I08".

Measured 2026-09-14 (UTC), core working tree on `6d798c0`, Pro `0da7e1d`,
Elixir 1.20.1, OTP 29, PostgreSQL on port 5490.

## What is guaranteed

Every feature has exactly one reporting source, declared as
`config :aurora_meter, feature_sources: %{name => :buffered | :events}` and
defaulting to `:buffered`.

For a feature whose source is `:events`, no quantity can reach
`aurora_meter_counters`, which is the only table a Pro reporter bills from
(`AuroraMeter.Pro.UsageReporter.report_one/5` reads it through
`AuroraMeter.Storage.load_counter/3`). The full nine-link chain, and the four
cuts this unit makes in it, are traced by symbol in `03c-i08-chain.md`.

For a feature whose source is `:buffered`, a recorded event is stored but its
export intent carries `{:ineligible, :feature_buffered}`, so the same usage is
not sent to a provider twice.

A configuration that declares one feature both ways stops the boot.

Every check was also **broken once on purpose** and the watching test confirmed
to fail: nine mutations, nine noticed, nine restored with an asserted restore.
See `03c-negative-controls.json`. The mutation that matters most here is
`projection-marks-dirty`, which makes `Counter.apply_projection/2` write
`pending_flush` and mark the key dirty; the flush-isolation test fails, which is
what makes that test a guard rather than a description.

## Prerequisites

A single configured source per feature, decided at a period boundary and applied
by a deploy. The source is read from a cache that
`AuroraMeter.Config.validate!/0` fills, so rewriting `:feature_sources` at
runtime changes the declaration and not the behaviour until the node is
validated again. That is deliberate: a source that could change between two
calls inside one period is the double count the key exists to prevent, and the
cached behaviour is itself asserted by
`test configuration a runtime change to feature_sources takes effect only when the cache is rebuilt`.

## Known limits

**A host that reads `aurora_meter_events` and bills it by hand** is outside the
invariant. It covers what this library writes to the table Pro bills from.

**An events-source feature has no day history at all.** `AuroraMeter.history/3`
returns zeros. Writing projected quantities into `aurora_meter_history` would
feed the Pro day rollup from the same units the export path sends, which is the
double count in a different table. `AuroraMeter.Events.stream/1` is the durable
series, and 04d gives Pro a day rollup from events.

**A source migration for a feature that is already being billed is not made safe
here.** Core refuses a dual declaration but cannot know whether a feature's
existing counter rows were ever reported. The watermark, the boot refusal when
`usage_reports` rows exist without a cutover row, and `usage_reports.source` are
Pro's and land in build unit 04c; Pro's `docs/usage-reporting.md` now says so in
the section this unit added. There is deliberately **no planned core test** for
the cutover, because core has no `usage_reports` table to refuse against; the
handoff is the paragraph in `docs/correctness.md`'s I08 "Known limits" and this
one.

**The cluster properties were exercised on one VM**, by driving
`AuroraMeter.Cluster.apply/3` directly. A real multi-node harness is 11d's.
