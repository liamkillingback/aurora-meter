# I09: corrections preserve immutable history and bounded net quantity

The invariant map names this file. It is the short version; the long versions
are `03e-step-order.md` (the order the bound and the duplicate check are taken
in), `03e-bound.json` (the concurrency numbers, ten seeds) and
`03e-eligibility.md` (what core tells the outbox).

## What is guaranteed

**Immutable history.** A correction is a new row in `aurora_meter_events` with
`kind = 'correction'` and `original_event_id` naming the fact it reduces. No
historical row is ever updated or deleted by any path in this unit;
`AuroraMeter.CorrectTest` / `test what a correction inherits the original row is
never updated` re-reads the original and asserts its quantity, its `recorded_at`,
its `seq` and its kind are unchanged.

**Bounded net quantity.** The cumulative magnitude of the corrections of one
original can never exceed that original's quantity. The sum is taken while the
original row is held under `SELECT ... FOR UPDATE`, in a statement that runs
after the lock is granted and therefore under a snapshot that includes every
correction committed by a corrector that held the lock before us. The loser is
told `{:error, {:invalid, [quantity: :exceeds_original]}}` and nothing is
written.

**Idempotence that survives the bound.** A repeated correction id is a
duplicate, including when the original is by then fully corrected. The duplicate
check runs before the bound check both before the lock and again under it.

**Inheritance.** A correction copies the original's feature, `occurred_at`,
`period_start`, `period_source`, `attribution`, `plan_id`, `plan_version` and
dimensions, inside the transaction that read the original under lock, so none of
them can drift from it. A September fact corrected in October changes
September's total (decision D08) and never reprices (D05).

**Provider honesty.** Every correction reaches the export seam, with an explicit
ineligibility reason when core can already tell delivery is impossible. None is
dropped and none is marked settled.

## Why a row lock and not a lease

`open-findings.md` X100: the one clock every node shares is not monotonic. A 300
second, 832,078 sample probe found `clock_timestamp()` stepping backwards nine
times, worst 439 ms, on a 32.5 second cadence. A bound implemented as "no other
corrector has touched this original in the last N seconds" would be inverted by
one of those steps, and the cost would be a double credit.

`SELECT ... FOR UPDATE` consults no clock. Postgres grants it, COMMIT, ROLLBACK
or the connection dying releases it, and it needs neither a timeout nor a
heartbeat. It is also the lock the ledger already uses for the same job
(`credits/ledger.ex`, `transact_outcome/1`'s callers), so the two financial
paths in core serialise the same way.

The lock is on the **original event row** and not on the totals row: the bound
is a property of one original, while the totals row aggregates many originals
and is also written by every concurrent `record/4` for that key, which is the
hot path. `AuroraMeter.CorrectConcurrencyTest` / `test twelve correctors of one
original I09 the lock that serialises correctors is the one on the original row`
holds `FOR UPDATE` on one original externally and asserts that a corrector of a
**different** original completes while a corrector of the **same** one waits.

## Prerequisites

Core schema version 7 or later: `kind`, `original_event_id`, the pairing check
constraint `(kind = 'correction') = (original_event_id is not null)` and the
partial index `aurora_meter_events_corrections_index` on
`(tenant_key, original_event_id) where kind = 'correction'`, which serves the
cumulative sum. A storage adapter declaring the `:corrections` capability; one
that does not is refused by the dispatcher with
`{:error, {:unsupported, :corrections}}` before it is called.

## Known limits

- **The provider half is not core's.** Whether a correction can still reach
  Stripe depends on the meter event adjustment window, which Aurora Meter Pro
  decides (build unit 04d) and quarantines with a `manual_adjustment`
  reconciliation item when it cannot. Core guarantees the item exists and
  carries a reason, not that it is deliverable. 04d evidences the other half in
  Pro.
- **Corrections of corrections are not supported in 1.0**, and are refused with
  `{:invalid, [original: :is_correction]}`.
- **The in-memory view is advisory**, as it is for every other path. A
  correction that would drive an ETS counter below zero re-seats the row from
  the durable total instead; `AuroraMeter.Events.total/3` is authoritative
  either way.
- **The legacy negative `track/4`** still exists for buffered features, mutates
  the counter in place and is bounded by nothing. 10c rewrites the storefront
  guides that teach it.
- **A host transaction changes durability, not correctness.** Inside one, the
  correction is `durability: :conditional`, the effects are deferred to
  `AuroraMeter.Events.after_commit/1`, and an outer rollback removes the row,
  its delta and its outbox item together.
