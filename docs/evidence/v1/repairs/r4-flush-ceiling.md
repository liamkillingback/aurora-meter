# Repair unit R4: the flush ceiling and the broadcaster's missing rescue

A repair unit, not a numbered build unit. It closes **X338**, the one finding in
the V1 programme marked release blocking, and with it **X348** and **X354**,
which are the same arithmetic seen from two other angles.

> **Standing rule.** No credentials, no customer identities, no unsanitised
> logs. Synthetic tenant ids only. Nothing here is invented: a command that was
> not run is named as not run.

Rule 4 applies. Nothing in this file ticks a checkbox, nothing is committed, and
the tree is left dirty for the reviewer.

## 0. The answer first

**X338 is closed.** A flush of 9,363 dirty counter keys, the exact count 08c
bisected as the first one that could not be sent, now works; so does 200,000,
which is the highest this unit measured. There is no ceiling left to bisect for,
because the number of statements now grows with the batch instead of the number
of bind parameters in one statement. The proof is not the unit tests: it is a
re-run of 08c's own `db_recovery` control, 12,000 rotating keys with history on
(24,000 dirty keys), a real ten second container stop, which **drained in 2,136
ms** where 08c's identical run waited its whole 60 second bound and reported
`24000 dirty keys, 24000 items in the pending batch`.

**X348 is closed.** The broadcast tick carries the `rescue` and the `catch` the
flusher has always had.

**X354 is decided.** `AuroraMeter.Supervisor` is now `max_restarts: 10,
max_seconds: 60`, chosen for stated reasons, with what a host should do when the
tree gives up written beside it.

**Not fixed, and filed rather than left**: the retry branch of `flush_batch/3`
reads its totals back one query per row, so a 100,000 key batch whose commit was
uncertain costs 100,000 round trips inside one transaction. It is correct and it
is slow, it existed before this unit and this unit did not touch it, and it is
now the largest thing left on this path. Written up in section 8 as **X372**.

## 1. What was wrong, in one paragraph

Postgres carries a statement's bind-parameter count in a 16-bit field, so one
statement takes at most 65,535 of them, and Ecto's `insert_all/3` spends one per
column per row. `AuroraMeter.Storage.Ecto.add_counters/1` built **one**
`insert_all` over a whole flush batch at seven parameters per counter row, so a
batch of more than `floor(65535 / 7) = 9,362` distinct counter keys could not be
**sent**: Postgrex refused to encode it and the query never reached the
database. `AuroraMeter.Flusher.failed/2` then retained the batch for an
idempotent retry, which is right for a transient failure and exactly wrong for
this one, so the dirty set never emptied and every later increment was buffered
with no way to reach the database. At the shipped 5,000 ms `flush_interval` the
threshold is 1,873 distinct keys per second. A host with 1,000 tenants across 10
features is already over it.

## 2. The fix, and why it does not cost the retry contract

`lib/aurora_meter/storage/ecto.ex` chunks every multi-row `insert_all` at a size
**derived from the schema**:

```elixir
@max_bind_params 65_535

def rows_per_statement(schema) do
  div(@max_bind_params, length(schema.__schema__(:fields)))
end
```

Derived and not written down, because a column added to
`AuroraMeter.Schema.Counter` in a later version lowers the real ceiling, and a
literal `9_362` here would keep the old one and fail again at a different row
count, which is the same defect with a new number. `__schema__(:fields)` counts
every field the schema declares, **including the autogenerated primary key that
`insert_all/3` does send**, so it is an upper bound on what a row can cost:
chunking by it can only ever be conservative. On this schema it gives 9,362 for
counters and 8,191 for the wider history row, and 08c's measurement of "seven
bind parameters per counter row" is exactly the seven fields
`AuroraMeter.Schema.Counter` declares.

**The idempotence question was the real work here, and the answer is that
chunking costs nothing.** `flush_batch/3` was already one `repo().transaction/1`
containing the receipt insert and both delta sets, and the receipt's
`on_conflict: :nothing` `inserted == 1` is what decides whether the deltas are
applied at all. Chunking happens *inside* that transaction: either the receipt
and every chunk commit together, or none of them do. A retry of the same batch
id finds the receipt, applies nothing and returns the current totals, exactly as
before. There is no state in which half a batch is committed and the receipt is
not.

Outside `flush_batch/3`, `add_counters/1` and `add_history/1` are public storage
callbacks whose callers have always been able to assume "all of these deltas or
none", because one statement gave them that for free. So a call that needs more
than one chunk now opens the transaction the single statement used to be, and a
call that fits in one takes the old path exactly: one statement, no transaction
of its own, the same round trips `flush_1k` always made.

Six call sites were chunked, not two. The finding names `add_counters/1` and
`add_history/1`; `upsert_counters/1`, `upsert_history/1`, `insert_events/1`,
`ensure_total_rows/3`, `insert_events_returning/3` and `apply_totals/4` build
multi-row `insert_all` statements from caller-sized lists in exactly the same
way. The two inside the durable record transaction are the ones that matter
beside X338: `AuroraMeter.record_batch/2` takes a list of any length and an
event row is wide, so that path had its own ceiling at a couple of thousand
events. Both are already inside a transaction their caller opened, so they chunk
without opening a second, and both sort the whole batch **before** the split, so
the chunks still acquire rows in one total order and L-03b-3's deadlock argument
is unchanged.

`move_totals/2`, the one multi-row write that passes its rows as `unnest`
arrays, has no per-row parameter cost and needed nothing. It is also the shape
that would have avoided this defect entirely, and is worth remembering the next
time a bulk write is added.

## 6. X348: the broadcast tick

`AuroraMeter.Broadcaster.handle_info(:broadcast, _)` now calls
`safe_broadcast/0`, which is `do_broadcast/0` with a `rescue` and a `catch`
around it, logs at `:error`, and reschedules either way. That is precisely what
`AuroraMeter.Flusher.do_flush/1` has always had, and the reason it is enough is
that the touched set is read fresh on every tick rather than carried in the
Broadcaster's state: a tick that cannot read the tables has nothing to publish,
and the next one publishes everything touched since.

**No new telemetry event.** `docs/telemetry.md` and `docs/api.md` are a
published contract that `AuroraMeter.Test.TelemetryCensus` holds the tree to,
and a broadcast that could not read ETS is an operational log line rather than
a metric to alert on; the thing worth alerting on is the Store crash itself,
which already reports. This is a judgement and it is written down so it can be
disagreed with.

`handle_call(:broadcast, ...)`, which is what `broadcast_now/0` calls, does
**not** rescue, deliberately: a caller asking for one broadcast and being told
`:ok` when nothing could be read is the silent pass this suite keeps finding.
There is no test asserting that, and the reason is in
`test/aurora_meter/broadcaster_test.exs`: proving it means letting the
Broadcaster die, the supervisor restarts it automatically, and an automatic
restart outside `AuroraMeter.KillTest` is exactly what that module's guard
forbids. An assertion is not worth spending a budget somebody else is counting.

The test opens the window with `Supervisor.terminate_child/2` rather than a
kill, for the same reason, and restores the Store in an `after` and again in an
`on_exit`.

## 7. X354: the restart intensity, decided

`lib/aurora_meter/supervisor.ex` is now:

```elixir
Supervisor.init(children, strategy: :one_for_one, max_restarts: 10, max_seconds: 60)
```

**The reasoning, which is also in the file.** The choice turns on an asymmetry.
Restarting a child of this tree is cheap: `init/1` creates ETS tables,
subscribes to one PubSub topic and schedules a timer, and none of them does IO
that can block. Giving up is not cheap: when this supervisor terminates, the
Store dies with it and the unflushed buffer in its ETS tables is gone, metering
stops, and the failure is handed to the host's own supervisor, which in an
ordinary Phoenix tree at OTP's defaults can take the whole application down. The
cost of tolerating one more restart is some wasted CPU; the cost of one fewer is
lost usage and an outage. Ten in sixty seconds leans the whole way towards
tolerating the flap.

It still gives up on a genuinely permanent failure, which is what an intensity
is for: a child that cannot start at all restarts as fast as the supervisor can
spawn it and spends ten in a few milliseconds. What the wider window buys is the
other shape, a child that dies every half minute under load, which used to
escalate into a total outage on the third one.

**What a host does when the tree gives up.** Metering has stopped and the
buffered deltas are lost, exactly as the `AuroraMeter.Flusher` moduledoc
describes for a VM loss. The host should let its own supervisor restart
`AuroraMeter` (counters rehydrate lazily from the database, so the loss is
bounded by one flush interval rather than by the whole period) and treat the
crash reports that preceded it as the incident: the tree going down is the
symptom, the repeatedly dying child is the cause. A host that cannot afford the
loss at all should be recording durable events (`AuroraMeter.record/4`) rather
than relying on the buffered path.

**The interaction with `AuroraMeter.KillTest`.** That module spends three
automatic restarts by design and its moduledoc was the only place the number
three was written down. Both moved together: the moduledoc now says three of
ten, the guard's failure message names the chosen intensity instead of OTP's
default, and a **new** test reads the flags back out of
`AuroraMeter.Supervisor.init/1` and fails if they and this module ever disagree.
`@budget` is still 3, because it counts the restarts this module makes and that
did not change.

The guard forbidding automatic restarts elsewhere was **not** relaxed. A wider
budget makes a stray restart survivable rather than harmless, and survivable is
not a thing to spend without saying so. X347 and X349 are made much less likely
by this change and are not made impossible by it; the guard is what makes them
impossible.

## 8. What this unit did not fix

**X372 (new): `flush_batch/3`'s retry branch reads its totals back one query per
row.** When the receipt insert finds the batch id already there, the adapter
returns the current totals by calling `load_counter/3` and `load_history/3` once
per row, inside the transaction. For the one-row retries that branch was written
for that is nothing. For a 100,000 key batch whose commit was uncertain it is
100,000 sequential round trips, and after this unit such batches are ordinary
rather than impossible. It is **correct**, which is why it is a finding and not
a defect in this repair: it returns the right totals and it double counts
nothing. It is now the largest cost left on this path, and it wants the same
treatment the write side just got: one query with the keys passed as arrays.

**`Flusher.failed/2` still has no notion of a permanent failure.** 08c filed this
beside X338 and it is still true: a batch that can never succeed is retried for
ever by a mechanism built for batches that can, and 08a's telemetry reports the
error count but not that one batch id has now failed a hundred times. X338 was
the one known way to manufacture such a batch and it is gone, which lowers the
urgency and does not answer the question. Left for the owner, in X338's row.

**The standalone-`add_counters/1` transaction is proved structurally, not by a
rollback.** `test/aurora_meter/storage_bind_ceiling_test.exs` asserts through a
recording repo that a multi-chunk call opens exactly one transaction and that
every statement is at or under the derived size. It does not force a failure
halfway and assert that nothing landed, because inside the Ecto SQL sandbox that
call is a nested transaction and a real statement error poisons the sandbox's
own transaction rather than the one under test. The flush path's atomicity, the
one the retry contract actually rests on, **is** proved end to end by the
retried-batch test and by the `receipt-ignored` control.

**`README.md` carries nine em and en dashes, and every one of them is at HEAD.**
Found by this unit's own dash check (`tmp/v1/r4-dashcheck.sh`) while confirming
its two-line edit was clean. The repository rule is that neither character
appears in user-facing copy, X337 fixed four of them in `components.ex` during
08c, and the README was missed. It matters more than the module did: `README.md`
is inside `package.files`, so it goes to Hex with every release and is the first
page a prospective customer reads. Lines 228, 240, 241, 447 and 449. **Not
fixed here**: unit 09c is editing that file in this wave and a sweep across it
would collide with theirs. Named for whoever holds the README next.

**Two of the six chunked call sites have no test of their own above the
ceiling.** `insert_events_returning/3` and `apply_totals/4` are covered by the
existing record and replay suites at ordinary sizes, and by reading; a
`record_batch/2` of four thousand events against the real database is not in
this unit's evidence. The ceiling they had is the same one, the derivation is
the same function, and the same control (`no-chunking`) covers the mechanism.
Naming it here rather than implying coverage.

And `no-rescue` fails **both** broadcaster tests rather than one, because the
second test asserts the pid at the end: without that assertion it passed with the
rescue removed, since a Broadcaster the supervisor had just replaced publishes
exactly as well as one that never died. That assertion was added when the control
found the test.

### The two that reported nothing the first time (filed as X373)

`receipt-ignored` and `no-rescue` were written as `if inserted == 1 or true do`
and as deleting the call to `safe_broadcast/0`. Both **failed to compile**:
`mix test` compiles with `--warnings-as-errors`, the first is an always-true
expression and the second leaves a function unused. The harness recorded both as
"discriminated" on a non-zero exit code, which is X300 exactly, and happening in
the controls written for a unit whose brief warns about it.

The detector was the other half of the fault. It looked for `CompileError`, and
a `--warnings-as-errors` build failure says "Compilation failed due to warnings"
and contains no such string, so it matched nothing and passed everything it
could not see (X325, X350). It now matches both, and the controls were rewritten
to invert the behaviour without introducing a warning: `is_integer(inserted)`,
which the compiler cannot fold, and a `rescue` clause that `reraise`s rather
than a deleted call.

Both are recorded here rather than quietly fixed, because the first run's table
said six of six and two of those six had run no test at all. Filed as **X373**,
with the general rule: under `--warnings-as-errors` a non-zero exit is not
evidence that a test ran, and a control harness must separate "the build failed"
from "the test failed" and say which.
