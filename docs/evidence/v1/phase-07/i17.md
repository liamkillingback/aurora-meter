# I17 Historical plans remain stable

Build unit 07a is I17's **owner**. Core `aurora_meter`, 2026-09-16.

## What this unit proves, and what it does not

`v1-release.md` section 17 asks three adversarial proofs of I17. **One of them
is in this unit.**

| Proof | Owner | State |
|---|---|---|
| Deploy a changed definition | **07a** | proved below |
| Explicit scheduled migration is the only thing that moves a tenant | 07b | **proved in 07b**: `core:docs/evidence/v1/phase-07/07b-i17.md`, and `PlanTransitionsTest` / `I17 an explicit scheduled migration is the only thing that moves a tenant's version` |
| A stale provider notification cannot move a version | 07c | **proved in 07c**: `pro:docs/evidence/v1/phase-07/07c-i17.md`, and `AuroraMeter.Pro.PlanRefTest` / `I17 a stale webhook for an ended subscription does not change plan_version` plus `I17 a webhook payload with an outdated price cannot move the version, because the object is retrieved fresh`. All three proofs are now in hand |

The guarantee as implemented: a plan is `(plan_id, version)`; a subscription
records the version it was sold; `AuroraMeter.Entitlements.plan/1` resolves
**that** version, from compiled code when it is there and from the registered
snapshot when it is not; and editing a version in place is refused rather than
applied.

## Forced contention, with numbers

`open-findings.md` X182 and X214: force it, count the contended branch, and
assert the count on an ordinary run.

`SKIP LOCKED` has no waiters by construction, so the observable is not a wait, it
is a **skip**. The test opens a second connection, takes `FOR UPDATE` on 12 of
40 unnamed rows and **holds** it, then runs one assignment batch of 1,000:

```
held = 12
skipped = @tenants - batch.assigned   # 40 - 28 = 12
assert skipped == held
assert elapsed < 2_000                # it did not wait
assert length(unnamed_ids(prefix)) == held
```

`skipped` is asserted on every ordinary run, not behind an environment variable.
Zero would not be a flake: it would mean either the holder never took its locks
or the statement no longer carries `SKIP LOCKED`, and the assertion message says
both. The holder then commits, the test waits for it (`assert_receive
{:released, ^holder}`, because `send/2` returns before the transaction ends), and
the next batch takes exactly the 12.

Negative control `e-no-skip-locked` removes `SKIP LOCKED`: this test fails and no
other does.

The disjoint-batch test counts differently: over 12 connections each draining in
batches of one, it asserts `total == 40` **and** that more than one connection
assigned at least one row, so a run in which the first connection took
everything is a failure rather than a pass.

## The kill results

Both use `AuroraMeter.Test.Kill.run/2` with a fault armed on
`assign_legacy_plan_versions`, and both assert the death reason is exactly
`:killed`. The fixture is **5,100** rows rather than 40 for the between-batches
case, because the batch is 5,000 and a fixture smaller than that has one
productive batch and nothing left to resume.

| Case | Fault point | Committed | Remaining | After a rerun |
|---|---|---|---|---|
| between batches | `after_commit_before_ack`, first batch | 5,000 | 100 | 0 unnamed, row count unchanged |
| inside a batch | `before_commit`, first batch | 0 | 5,100 | 0 unnamed |

The remaining count is asserted **exactly** (`partial == 5_100 - 5_000`), not as
"some rows remain": a loop that committed a partial transaction would pass the
looser assertion.

## Criterion 4 and criterion 9: what carries the claim

Both are the criteria whose failure mode is a customer silently losing or
gaining entitlements, so both were run against a negative control that reverts
the mechanism, and criterion 4 was run a second time with only the assertion I
believed was load bearing relaxed (`open-findings.md` X242).

**Criterion 4** (`I17 a tenant subscribed before version 2 exists keeps version 1
after version 2 is effective`). A tenant subscribes to `:versioned` while version
1 is effective. The test records the version, price, `quota/2` limit,
`feature_value/3` for `:seats`, `entitled?/2` for `:api_access` and the recurring
credit amounts and rollover caps. It then swaps in
`AuroraMeter.Test.VersionTwoLivePlans`, which is the same module with version 2's
`effective_at` moved into the past, asserts `Plans.get(:versioned).version ==
"2"`, invalidates the subscription cache, and asserts every recorded figure is
unchanged and the row still reads `plan_version: "1"`.

- Control `a2-plan-ignores-pin` makes `Entitlements.plan/1` resolve
  `Plans.get(id)` instead of `Plans.get(id, version)`: **4 tests fail**,
  including this one.
- Control `a3` applies the same break and relaxes **only** the
  `AuroraMeter.plan(tenant).version == "1"` assertion: **the same 4 tests still
  fail**. So the version label is not the single load-bearing line; the price,
  quota, feature value and credit assertions discriminate on their own.

With the change reverted this test fails on the price (2,000 against 3,000), the
quota (1,000 against 2,000), the seats value (5 against 25) and the credit
amounts (5,000,000/1,000,000 against 9,000,000/3,000,000), in that order.

**Criterion 9** (`I17 a tenant keeps version 1's limits when version 1's block is
deleted from the module`). The same tenant, with
`AuroraMeter.Test.VersionOneDeletedPlans` swapped in: a module whose only
`:versioned` block is version 2. The test asserts `Plans.get(:versioned, "1")` is
not nil (so it came from the snapshot), then that the resolved plan's version,
price, `:ai_generations` limit, `:seats` value and credit amounts are version
1's, and that `quota/2` and `feature_value/3` agree. It captures the log and
asserts there is no `[error]` line and no dropped-feature line, which is the
"logs no error other than the documented one" half of the criterion.

- Control `b-no-snapshot-fallback` makes `Storage.Ecto.list_plan_versions/1`
  return `[]` for both clauses, so neither the registration's cache load nor a
  later miss finds anything: **3 tests fail**, including this one.
- With the change reverted this test fails at
  `assert plan, "version 1 should have resolved from the stored snapshot"`,
  named so the failure says what happened rather than `nil.version`.

The **first** attempt at the criterion-4 control anchored on the wrong
occurrence of `Plans.get(id, version)` (there are two; `resolve_version/2` comes
first in the file) and broke `subscribe/3` instead. It reported
"DISCRIMINATED" and criterion 4's own test was **not** in the failure list, which
is how the mistake was caught. Both controls are kept, under different names.

## The conflict message

```
Aurora Meter refuses to reprice an existing plan version. The commercial content
of 1 compiled plan version(s) differs from the snapshot registered for them:

  * plan versioned version 1: stored 1b0d3668c321, compiled 4dab38f9fe3e

Every subscription pinned to one of those versions was sold the stored
definition. Publish the change as a new version instead, for example:

    plan :versioned, version: "2", effective_at: ~U[2026-01-01 00:00:00Z] do
      # the new price and limits
    end

Or revert the edit. Setting `config :aurora_meter, plan_version_conflict: :warn`
logs this instead of raising, which is the transition-release default and not a
fix. The stored definitions are in aurora_meter_plan_versions:

    SELECT plan_id, version, encode(fingerprint, 'hex'), definition
    FROM aurora_meter_plan_versions ORDER BY plan_id, version;
```

It names the plan, the version, both fingerprints (first 12 hex characters), the
remedy with a worked `plan` block, the configuration key that downgrades it, and
the query that shows the stored definition. The `AuroraMeter.PlanVersionConflictError`
struct carries `conflicts`, a list of maps with `plan_id`, `version`,
`stored_fingerprint` and `compiled_fingerprint`, for a host that rescues it in a
release task.

Control `k-no-conflict-check` makes every comparison equal: 2 tests fail.

## Known limits

- A feature or recurring credit name in a stored snapshot is read back with
  `String.to_existing_atom/1`. A name with no atom on the node is dropped and
  logged once per version per node. Invisible to every entitlement function,
  which all take atoms; **not** invisible to code that enumerates
  `plan.features`.
- `effective_at` is outside the fingerprint, so moving it is not a conflict. See
  `07a-fingerprint.md` and finding X290.
- A storage adapter without the `:plan_versions` capability leaves compiled code
  as the only authority, and a version deleted from code then becomes
  unreadable.
