# 07b and I16: worker scheduling is not an exactly-once assumption

Build unit 07b, contributor to I16. The invariant's owning evidence file is
`core:docs/evidence/v1/phase-05/i16.md`; this page is the transitions half and
is linked from it.

## The guarantee this unit adds

`AuroraMeter.Subscriptions.apply_due_transitions/1` and
`AuroraMeter.Oban.PlanTransitions` are safe to run twice, from two nodes, at any
interleaving, because **every effect is an update conditional on the transition
still being `pending`**. One caller applies; every other caller affects zero
rows and counts a `skipped`, which is a number in the return value rather than
an error.

No lease. No fence. No duration. Nothing in the exclusion can be inverted by a
clock that steps backwards (`open-findings.md` X100), because there is no clock
in the exclusion at all: it is a row lock plus a predicate on a state column.

## PlanTransitions keeps no checkpoint, deliberately

The other core sweeps run through `AuroraMeter.Operations.run_batches/3` and
keep a cursor in `aurora_meter_checkpoints`. This one does not, and the reason
is that its resume rests on a **predicate** rather than on a position: a killed
run leaves every un-applied tenant with `transition_state = 'pending'`, and the
next run finds exactly those from the partial index core schema version 10
creates. There is no cursor to rewind and no cursor to go stale.

`open-findings.md` X242 is the rule being followed: when a worker's resume rests
on a predicate rather than on a cursor, its row should say so instead of
borrowing a control that cannot discriminate for it. The kill test therefore
asserts the **complement** (the tenants the run had not reached are still
pending, and the next run applies exactly those and nothing twice) rather than a
cursor value. The `cursor` the operation returns is paging inside one run, not
durable state.

## The named tests

All in `test/aurora_meter/plan_transitions_concurrency_test.exs`, none inside a
`describe` block (`open-findings.md` X196), all listed in
`docs/correctness.md`. The module runs on independent non-sandbox connections
through `AuroraMeter.Test.Connections`, because the sandbox serialises the very
contention these are about.

| Line | Test | What it establishes |
|---|---|---|
| 99 | `I16 twelve independent connections scheduling one ref produce one transition row` | acceptance criterion 2. Twelve `{:ok, transition}` results carrying **one** id, one row in `aurora_meter_plan_transitions`, one `transition_ref` on the subscription, and the contended branch counted from telemetry: `%{scheduled: 1, idempotent: 11}` |
| 125 | `I16 twelve independent connections applying one due transition apply it once` | acceptance criterion 3. `applied=1 skipped=11`, one `state = 'applied'` row, one subscription row on the new pair, and **12 of 12** processes observed waiting on the subscription row lock |
| 163 | `I16 a cancel racing an apply yields exactly one terminal state` | ten rounds, two racers behind a rendezvous. In every round the audit row is `applied` xor `cancelled`, the subscription's plan agrees with it, and **exactly one** racer reports a win: the loser fails its own predicate and says so |
| 208 | `I16 a provider sync racing an apply yields one terminal state and one plan` | ten rounds. Whichever wins, the mirror and the audit row agree, and a cancelled transition carries `provider_override` with the provider's plan on the row |
| 250 | `I16 two Oban jobs from two nodes apply one transition` | one applied, one skipped, through `perform/1` with no injected clock, which is the path a crontab tick follows |
| 277 | `I16 the applier killed before commit leaves the transition pending` | `kill -9` at the conditional update, before commit. The plan is unchanged, both rows still `pending`, and the next run applies it |
| 301 | `I16 the applier killed after commit and before cache invalidation converges` | acceptance criterion 4, measured. See `07b-lag.md` |
| 342 | `I16 the applier killed mid-batch leaves the applied tenants applied and the rest pending` | four tenants, killed after the second commit. Two applied, two pending, and the next run applies **exactly two** and skips nothing |

## What is not proved here

The **crash between a provider update and the local commit** half of G07 bullet
3 is only half core's. Core's half is that a `confirm: :provider` transition
stays `pending` and visible until `confirm_transition/3` records the provider's
reference, and that the call is idempotent under redelivery
(`test I17 confirm_transition is idempotent under redelivery of the same
provider_ref`, `test I17 confirm_transition with a different provider_ref on an
applied transition conflicts`). Calling the provider and reconciling after a
crash is **07c's**.
