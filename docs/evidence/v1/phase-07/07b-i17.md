# 07b and I17: historical plans remain stable

Build unit 07b, contributor to I17. The invariant's owning evidence file is
`core:docs/evidence/v1/phase-07/i17.md` (07a's); this page is the transitions
half and is linked from it.

## The three adversarial proofs, and who owns which

`v1-release.md` section 17 asks three things of I17.

| Proof | Owner | State |
|---|---|---|
| Deploy a changed definition and it raises rather than repricing | **07a** | proved in `i17.md` |
| **An explicit scheduled migration is the only thing that moves a tenant's version** | **07b** | **proved here** |
| A stale provider notification cannot move the version | **07c** | not in this unit, and not claimed here |

## The one this unit owns

`test I17 an explicit scheduled migration is the only thing that moves a
tenant's version` (`test/aurora_meter/plan_transitions_test.exs:618`) has two
halves and both matter.

**Half one, deploying does nothing.** A tenant on `:versioned` version 1, with
`AuroraMeter.Test.VersionTwoLivePlans` swapped in so version 2 is effective
**now**: `Plans.get(:versioned).version` is `"2"`, `AuroraMeter.plan/1` still
answers `"1"`, the hard limit is still 1,000 rather than 2,000, and the
subscription row still names version 1.

**Half two, the transition does everything.** A `schedule_transition/3` with an
explicit `version: "2"` and a reference, applied at its boundary, moves them:
the plan is version 2, the limit is 2,000, and the audit row records
`from_version: "1"`, `to_version: "2"` and the effective instant the schedule
carried.

Nothing else in the package writes `plan_version` on a subscription row that
already has one. `AuroraMeter.Plans.register!/0` fills only NULLs (07a);
`Storage.put_subscription/1` can only replace a column the caller supplied, and
the transition columns are outside `Subscription.syncable/0` entirely (07a's S4
fix, which this unit depends on and exercises from the transition side).

## What a transition never does

**It never rewrites history.** The previous `(plan_id, plan_version)` is copied
into `from_plan_id` and `from_version` before the subscription row changes, and
`plan_effective_at` becomes the transition's **boundary**, not the instant the
worker noticed
(`test I17 an applied transition changes plan_id, plan_version, fingerprint and
effective time`, line 358). That column is what 07c's attribution walks.

**It resets nothing** (lower-level invariant L17.9).
`test I17 applying a transition deletes no counter, history, event, transaction
or lot row` (line 660) counts `aurora_meter_counters`,
`aurora_meter_history`, `aurora_meter_events`,
`aurora_meter_credit_transactions` and `aurora_meter_credit_lots` before and
after and asserts the five counts are identical, and then asserts the two tables
it **does** own changed, because five unchanged counts would also be true of a
run that did nothing. `test I17 usage recorded before the boundary stays in its
period after the transition applies` (line 692) is the same property from the
tenant's side.

## The rest of the named tests

`test/aurora_meter/plan_transitions_test.exs` (50 tests), 
`test/aurora_meter/plan_transition_precedence_test.exs` (11),
`test/aurora_meter/plan_preview_test.exs` (14). Every description begins with
`I17` or `X288`, none sits inside a `describe` block, and every `I17` one is
listed in `docs/correctness.md`.

Groups, with the first line of each:

- **scheduling and its refusals** (89 to 246): the default boundary from the
  tenant's own period source, the default version resolved at the **effective
  time**, and eight refusals each naming its field.
- **idempotency, replace and cancel** (257 to 330).
- **applying** (337 to 535): due and not due, what changes, `applied_at`, the
  terminal `failed` state that is never retried, the provider-confirmed pair,
  and `confirm_transition/3`'s four cases.
- **paging** (538, 571): the applier's cursor, and a read-only scan that proves
  the keyset partitions the pending set with no repeat and no gap (finding
  X298: the applying walk cannot tell a working cursor from a broken one,
  because the scan advances by doing the work).
- **the two structural proofs** (710, 733): no transition source names a price,
  read from the AST rather than by grep; and a zero-price transition issues the
  identical sequence of SQL statements to a priced one.
- **custom periods** (792 to 845): calendar, subscription-aligned, weekly, and a
  broken source that raises `AuroraMeter.Period.InvalidPeriodError` naming the
  module.
- **precedence** (the whole of `plan_transition_precedence_test.exs`): the
  provider table in `07b-state-machine.md` section 4.
- **preview** (the whole of `plan_preview_test.exs`): the diff, the three
  provider outcomes, and that it writes nothing.

## Evidence for the claim this page does not make

A stale provider notification moving a version is **07c's**, and nothing here
should be read as proving it. What this unit provides towards it is the seam:
`confirm_transition/3`'s idempotency, and the precedence rule that a provider
write naming a plan core did not expect cancels the transition rather than
silently applying something else.
