Build unit 09b, task 09.10. `product-workspaces/aurora_api` (the Aurora API
Starter template, version 1.2.0, `mix.exs:7`) is the only consumer of these
packages that is not a test. It is **read only** to this unit: nothing in it was

## The build document's table was an undercount

`09b-installers-and-host-compatibility.md` lists **seven** call sites and this
report is required to carry "all seven". There are **thirty-one**, across
fourteen modules. The seven in the build document are all real and all still
present; the table below is the full set, because a compatibility report that
covers a fifth of the surface tells the owner nothing about the other four
fifths. The seven the document named are marked in the last column.

Counted as a call site: one source line naming an `AuroraMeter.*` module,
function, behaviour or type. Prose mentions in a `@moduledoc` are listed
separately at the end, because they are documentation the template will have to
update and not code that will stop compiling.

## The one V1 change that is breaking, and why it does not reach this template

**C9 / D12**: both packages narrow `phoenix_live_view` from
`"~> 0.20 or ~> 1.0"` to `"~> 1.0"` (this unit). `aurora_api` is a Phoenix 1.8
application on LiveView 1.x, so it resolves the narrowed requirement unchanged.
A template user who had pinned LiveView 0.20 would hit a resolution conflict, and
the upgrade route is in `docs/support-policy.md`: move to LiveView 1.0, or drop
the optional dependency and keep using the package headless.

## What this report is not

It is not a test. `aurora_api` is a separate repository that this programme does
not build, so nothing here is asserted by `mix test` in either package. The
guard against it going stale is that 09e and 11c install the packages
clean-room from candidate archives (invariant I21), which is a stronger check of
the same claim and does not depend on this file being reread.
