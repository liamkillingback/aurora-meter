# 02a: the moduledoc and spec gaps, before and after

Build unit 02a's implementation sequence says to write A03 and A04 first, run
them, and record the failure list **before** changing anything, because that
list is the inventory's raw material. This is that list.

Method: `Code.fetch_docs/1` for the module doc and for one entry per function
definition (a function with default arguments appears once, at the maximum
arity, which is the arity the `@spec` covers), and `Code.Typespec.fetch_specs/1`
for the specs. Functions carrying `@doc false` are excluded, because A02 already
keeps them out of `docs/api.md` and a hidden function is not public surface.
Compiler-generated reflection functions (`__struct__`, `__schema__`, and
anything else spelled `__name__`) are excluded.

## Step 1: the run before any edit

Command: `mix test test/aurora_meter/api_inventory_test.exs` with A03 and A04
implemented and both attribute lists empty. Exit 2, 3 of 4 tests passed.
Log: `tmp/v1/02a/core-step1.log`.

### A03, modules without a `@moduledoc`

**None.** Every module compiled from `lib/` either carries real module docs or
carries `@moduledoc false` deliberately. That is worth stating plainly rather
than leaving as an empty section: the gap this unit expected to find in core does
not exist, and the work that remained was classification, not writing.

## Step 2: what was done about each

Nothing was given a `@spec` and nothing was renamed. All twelve are allow-listed
with a reason, which A04 requires, and a third test fails when an entry stops
being needed, so the list cannot outlive its reason.

| Entry | Reason |
|---|---|
| `AuroraMeter.Clock.Fixed.child_spec/1` | Generated by `use Agent`. The contract is OTP's `Supervisor.child_spec/0`, and a hand-written spec would restate it at the risk of drifting from it. Adding one would also mean `defoverridable`, which is a code change, and this unit changes no code. |
| `AuroraMeter.Flusher.child_spec/1` | Generated by `use GenServer`. Same reason. |
| `AuroraMeter.Components.usage_meter/1` and the three others | HEEx function components. Their typed contract is the `attr/3` declarations, which ExDoc renders on the function's own page; a `@spec` would say `map() -> Phoenix.LiveView.Rendered.t()`, whose return type belongs to an optional dependency and whose argument type says nothing a reader needs. |
| The six `AuroraMeter.Plans` macros | The plans DSL. They are usable only inside a module that `use`s `AuroraMeter.Plans`, and a spec on a macro describes the AST it receives rather than the DSL it accepts, which is the opposite of informative. |

All twelve appear in `docs/api.md`: the four components in section 1.12 tagged
`optional-dep`, the six macros in section 1.5, and the two `child_spec/1`
functions in neither, because a host does not call them (it names the module in a
supervision tree, and `AuroraMeter.Clock.Fixed.start_link/1` is what section 10
lists).

## Step 3: the run after

Exit 0, 16 of 16. Log: `tmp/v1/02a/core-step4.log` and, at the unit's final
state, `tmp/v1/02a/core-check-final.log`.

The three A04 tests are:

- "every public function of a non-internal module has a spec"
- "every spec exception carries a reason" (a blank or missing reason fails)
- "no spec exception is stale" (an entry whose function has since gained a spec,
  or which no longer names a public function, fails)

## A note on what A04 does and does not cover

A04 skips modules in `@internal_modules`, which is why
`AuroraMeter.Storage.Ecto`'s twelve unspecced callback implementations do not
appear above. They are `@doc false` as well as internal, so they are doubly out
of scope; the specs that matter for an adapter author are the `@callback`
declarations on `AuroraMeter.Storage`, which all exist.

It also skips `@doc false` functions in public modules, which is why
`AuroraMeter.Billing.Noop`'s four callback implementations do not appear. Their
contract is `AuroraMeter.Billing.Provider`'s.
